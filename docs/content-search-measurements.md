# Document content search: measurements (VFS-2 prototype)

Companion to `specs/vfs-2-content-search/spec.md` and `docs/content-search-design.md`. Every
figure carries one of the labels of the design doc: **[measured]** (here, with how),
**[published]** (third party, not reproduced) or **[estimate]** (our arithmetic; assumptions
given). Nothing here was measured on the target PC.

## Machine and conditions

- Development Mac: Apple M1 Pro (8 performance + 2 efficiency cores), 16 GB RAM, internal
  NVMe SSD, macOS 26 (Darwin 25.6). Rust 1.100, release builds (`opt-level 3`, thin LTO).
- **The Mac was shared with four other agent sessions building and testing in parallel.**
  The load average during the 20,000-document run is in the scale section. The extraction
  worker runs in macOS's background band (throttled CPU and disk I/O, VFS-2 R5), so its
  wall-clock time depends on that load. **CPU seconds** are reported next to wall-clock time
  because they do not.
- Everything was read from the SSD with a warm OS cache for most files: these figures carry
  no HDD seek cost and no antivirus cost. The estimates section adds both.

## Corpus

Generated by `bench/content-corpus/make_corpus.py` (deterministic per seed):

- **Evaluation set** (`eval`, seed 7): 448 valid documents, 40 per format plus 80 PDFs:
  DOCX, DOC, PDF, XLSX, XLS, PPTX, PPT, ODT, RTF, TXT. Spanish text from a vocabulary rich in
  accents and `ñ` (`cigüeña`, `amortización`, `Peñalara`), 60–12,000 words per document
  (log-normal around 1,200), one marker sentence per document (`el señor Muñoz pagó la
  factura de la calefacción…`) to check reading order. PDFs come from two producers:
  fpdf2 (15 % two-column layouts, 30 % with line-end hyphenation of long words) and
  LibreOffice (Writer → PDF). DOC, XLS and PPT are LibreOffice conversions of generated
  DOCX/XLSX/PPTX, i.e. real binary Office 97 files.
- **Real PDFs**: 8 documents of the Spanish official gazette (BOE), 1–149 pages, with the
  reference text from the BOE's HTML version (`make_corpus.py real`). Legal texts are not
  copyrighted in Spain (LPI art. 13); they are not committed, only the procedure.
- **Hostile set** (53 files): for each format a half-truncated file, the first 100 bytes, a
  copy with 1 % of its bytes randomised, random bytes and an empty file; plus a JPEG named
  `.pdf`, an RTF and an HTML named `.doc` (both happen in old archives), a password-protected
  DOCX (encrypted OOXML) and PDF (AES-256 user password), a PDF with only an owner password, a
  scanned PDF without a text layer, a DOCX zip bomb (1 GB `document.xml`), and three large
  valid files (2.8 MB TXT, a 1,000-page PDF, a 600,000-word XLSX).
- **Scale set** (`bulk`, seed 11): 20,000 documents, 921 MB, mix PDF 40 % (half fpdf2, half
  LibreOffice), DOCX 20 %, DOC 8 %, XLSX 10 %, XLS 4 %, PPTX 4 %, PPT 2 %, ODT 3 %, RTF 3 %,
  TXT 6 % **[estimate of a personal archive's mix]**, in 14 Spanish folder names.

Limits of the corpus: generated text is a bag of real Spanish words, so ranking quality is
not meaningful (most words occur in most documents); fidelity is. Real archives hold scanned
faxes, odd encodings and producers we did not generate; the BOE PDFs are the only
third-party files.

## Extraction libraries

Harness: `bench/extract-eval` (standalone cargo package; each backend behind a feature).
Each file is extracted in a fresh child process with a 30 s limit, as the real worker does
in isolation, and the text is scored against the truth:

- **token recall**: share of the truth's words (lower-cased, accents kept) found in the
  output, as a multiset;
- **accent recall**: the same over words with a non-ASCII letter only;
- **marker in order**: the marker sentence appears contiguous (reading order, columns);
- **hyphen words**: of 8 long words split with a line-end hyphen in the PDF, how many come
  out whole (before the analyzer's own rejoining, which `vfs-content` adds).

Times include starting the child process (~8 ms) and some runs overlapped with compilations,
so throughput is comparative, not absolute.

### Coverage, fidelity and robustness [measured, `eval` set]

| Library | Version, licence | Formats extracted | Token recall | Accent recall | Marker in order | Hyphen words | Hostile files: crash / hang | Peak RSS |
|---|---|---|---|---|---|---|---|---|
| **Xberg** (successor of Kreuzberg), pure-Rust PDF backend | 1.4.2, MIT | all 10 (+ODS/ODP, RTF, MD, CSV) | 99.8 % | 99.8 % | 99.3 % | 93.3 % | 0 / 0 | 83 MB (XLSX of 600 k words); 64 MB (149-page PDF) |
| pdf-extract (lopdf) | 0.12.1, MIT | PDF | 99.4 % | 99.1 % | 96.2 % | 93.3 % | 0 / 0 | 26 MB |
| pdf_oxide | 0.3.78, MIT/Apache-2.0 | PDF | 99.6 % | 99.3 % | 97.5 % | 100 % | 0 / 0 | 46 MB |
| PDFium via pdfium-render | chromium/8165 build (pdfium-binaries), BSD-3 + Apache-2.0; binding 0.9.5 MIT/Apache | PDF | 99.4 % | 99.1 % | 96.2 % | 93.3 % | 0 / 0 | 28 MB |
| calamine | 0.38.0, MIT | XLS, XLSX, ODS | 99.8 % | 99.8 % | 100 % | — | 0 / 0 | 18 MB |
| zip + quick-xml (60 lines of our own) | MIT | DOCX, PPTX, ODT | 100 % | 100 % | 100 % | — | 0 / 0 (its 64 MB inflate cap stops the bomb) | 132 MB (bomb) |
| *pdftotext (Poppler, GPL) — reference only, not a candidate* | 26.x, GPL | PDF | 99.6 % | 99.3 % | 97.5 % | 100 % | 0 / 0 | 14 MB |

- Fidelity on PDFs is a near tie: every PDF library, Poppler included, scores 95.5 % token
  recall on the BOE PDFs (the misses are running headers, page numbers and footnote markers
  that the HTML reference lacks) and 100 % on two-column fpdf2 layouts.
- Accents and `ñ` survive in every library on every producer; no mojibake was seen.
- No library crashed, hung or ran out of memory on any hostile file. The worker's isolation
  is still needed: the corpus is small, and the archive is decades old.
- Password handling differs: Xberg reports "PDF is encrypted" (mapped to `skipped`), and an
  encrypted DOCX is recognised by its OLE container (`skipped`). pdf_oxide returns an empty
  text for the encrypted PDF instead of an error.
- Corrupt input mostly fails cleanly. With Xberg, half-truncated PDFs and RTFs return the
  readable part, and random bytes named `.txt` or `.rtf` come out as garbage text (indexed;
  harmless, and capped by the analyzer's 40-character word limit).

### Choice: Xberg

Chosen because it is the only candidate that covers **every format in scope in one
dependency, legacy Word, Excel and PowerPoint included**, with fidelity equal to the best PDF
library and to Poppler, clean failures on every hostile file, password detection, pure Rust
(no native library to ship or sign per platform, no C toolchain beyond what SQLite already
needs), and an MIT licence.

What it costs, and the rejected alternatives:

- **+32–34 MB of binary** and a 3.5-minute clean build. The composite route —
  pdf-extract (or PDFium) + calamine + our own zip/XML code — adds only 2.5 MB (or 3 MB +
  7.6 MB of native library) but **covers neither DOC nor PPT nor RTF**: in a decades-old
  Spanish archive, Word 97–2003 files are a large share (8 % of our mix is a guess), and
  writing a Word binary (piece table, CP-1252/UTF-16 runs, fast-save) or PowerPoint binary
  parser ourselves is the riskiest code in the whole feature. Rejected for this step.
- **PDFium**: fastest on large PDFs and the most battle-tested parser, but a native
  library per platform (download, ship, code-sign on macOS), PDF only. Kept as the upgrade
  path if real archives show Xberg's PDF backend failing or too slow (Xberg also offers a
  `pdf-pdfium` backend).
- **pdf_oxide**: best hyphenation handling, but slow on the 1,000-page PDF, misreports
  encrypted PDFs as empty, and adds 6.4 MB for PDF only.
- **Poppler (`pdftotext`) and MuPDF**: GPL and AGPL; excluded by licence (design doc).
- **Apache Tika**: needs a Java runtime; excluded for footprint.

Risks taken with Xberg: a young project with one vendor (renamed from Kreuzberg in 2026),
fast-moving 1.x releases (pinned with `=1.4.2`), an async API that needs a Tokio runtime
(confined to the worker), and its PDF backend's speed on large PDFs.

## Full-text engine: SQLite FTS5 vs Tantivy

Harness: `bench/index-eval` (standalone package). Both engines index the same 20,000 texts
taken from the content store of the scale run (302.8 MB of extracted text, 15 KB per
document on average) with the same analysis (words, lowercase, Snowball Spanish stem, accent
fold): FTS5 receives keys analysed in Rust, as `vfs-content` stores them; Tantivy analyses
with its own `SimpleTokenizer → LowerCaser → Stemmer(Spanish) → AsciiFoldingFilter`, one
indexing thread and a 50 MB writer budget (what a low-memory PC would get). Positions are
indexed in both (phrase queries). Queries: the 40 of the scale run (common words, accent
variants, AND pairs, phrases, a word in no document, and the marker words of 15 random
documents, each shared by 1–4 documents), top 20 by BM25, median of 5 runs after a warm-up, warm OS cache.

| [measured] | SQLite FTS5 (keys pre-analysed) | Tantivy 0.27 |
|---|---|---|
| Build time, 20,000 documents | 18.4 s (13.9 s of it is our analysis in Rust) | 11.1 s |
| Index size | 76 MB in the content store (dbstat; 86 MB file after `optimize` without vacuum) | 56 MB |
| Index size per 1,000 documents | 3.8 MB | 2.8 MB |
| Peak memory while building, above loading the texts (212 MB) | +74 MB | +276 MB |
| Query p50 / p95 / max | 7.8 / 17.7 / 24.1 ms | 0.04 / 3.1 / 5.6 ms |
| Peak memory of the query process | 11 MB | 15 MB |
| Binary size added | 0 (SQLite is already linked for the name index) | +5.5 MB |
| Stores | one SQLite file, transactions shared with the queue and the text | a directory of segments beside SQLite; needs its own consistency check after a crash |

**Choice: FTS5.** Tantivy is faster and its index is 26 % smaller, but FTS5 is already well
inside the latency budget (p95 18 ms against 150 ms), costs no binary size, needs a quarter of
Tantivy's memory while indexing on a PC that is short of it, and keeps the queue, the text,
the chunks and the full-text rows in one SQLite file updated in one transaction: nothing can
drift after a crash or a power cut. The custom-tokenizer variant of FTS5 from the design doc
was not needed: analysing in Rust and storing space-separated keys gives the same matching
with no unsafe glue. **Revisit** if the index size on the real archive matters more than
expected (the difference is about 1 MB per 1,000 documents **[estimate from the table]**)
or if query latency on the target PC's HDD misses the budget.

## Scale run: 20,000 documents

`bench/content-corpus/measure.py` with the release CLI built with `--features content`:
`vfs index`, then `vfs content-index`, then 40 queries. That build runs every command on the
worker's counting allocator (one atomic add per allocation), so its query figures include that
cost. One worker, one file at a time, worker
in the background band. Load average on the Mac during the run: median 18, range 8–60
(other sessions), so wall-clock figures are pessimistic for this machine and CPU seconds are
the comparable figure. All values **[measured]**.

| | Value |
|---|---|
| Documents, source size | 20,000; 921.0 MB (46 KB per document on average) |
| Outcome | 19,998 indexed; 2 failed by timeout (worker starved under load; they are retried once on the next run, D7) |
| Wall clock | 1,720 s (28.7 min): 11.6 documents/s, 0.54 MB/s |
| CPU | worker 669 s (**33 ms per document**); indexer process 27 s (1.4 ms per document: analysis and SQLite) |
| Peak memory | indexer process 19 MB; worker 48 MB (123 MB on the evaluation set, whose large files are bigger) |
| Bytes read | 920.9 MB = **100 % of each file, read once, sequentially**; a second run on unchanged files read 0 bytes and opened no file (AC-6 test) |
| Extracted text | 302.6 MB (15.1 KB per document); none hit the 1 MB cap |
| Content store | **236.5 MB**: compressed text 134.6 MB (deflate, 44 % of the text), FTS5 index 76 MB, chunks 4.4 MB (180,825 chunks, 9 per document), rest metadata |
| Store per 1,000 documents / per GB of source | **11.8 MB / 257 MB**; per MB of extracted text 0.78 MB |
| Name index of the same files, for scale | 2.7 MB |
| Query CPU, warm connection, 40 queries (median of 7) | p50 24 ms, p95 53 ms, max 63 ms |
| Query wall clock, warm (load 60+ at the time) / cold first query of a process | p50 47 / 407 ms, p95 529 / 1,028 ms |

The 40 queries include 25 common-word and phrase queries that, in this synthetic corpus,
match more than 10,000 of the 20,000 documents (the vocabulary is small, so nearly every word
is everywhere), and 15 marker words in 1–4 documents each. Marker queries take 0.3–7 ms of CPU;
the common ones 20–63 ms, because FTS5 computes BM25 for **every** matching document before
sorting: the cost grows with the number of matches, about 2–3 µs per matching document on
this Mac including the 20 snippets. The first query of a process pays for a cold SQLite page
cache; the app keeps one connection open (`Searcher`), so only its first content query pays it.

Fidelity at scale: for the 15 sampled marker words, each query returned exactly the
documents whose text holds that word (its own document plus any other the generator gave the
same marker; 15 of 15); `"contrato de alquiler"` as a phrase matched 6 documents versus 10,000+ for the
words apart.

## Estimates for the target PC

All **[estimate]**. Assumptions, each a guess to be replaced by Fase 2 measurements:

- A1. Real documents average **300 KB** on disk and **20 KB of text** (3,000 words, the
  design doc's figure); the synthetic ones were 46 KB and 15 KB.
- A2. The HDD costs 2 random accesses per file (metadata + data) at ~12 ms each, then reads
  at an effective 60 MB/s with the Synology client competing.
- A3. Microsoft Defender's real-time scan adds **20–100 ms per opened document** (central
  50 ms): Office files are ZIP containers it unpacks, PDFs are scanned too. Unmeasured.
- A4. One core of the target CPU is 2–3× slower than an M1 Pro performance core; extraction
  CPU grows with text: 33 ms per 15 KB on the Mac → 45 ms per 20 KB → **90–135 ms** there.
- A5. Background priority and other disk users stretch the total by 1.2–2×.

Per document: 24 ms seeks + 5 ms reading + 50 ms Defender + 115 ms CPU + 5 ms indexing ≈
0.2 s, × 1.5 ≈ **0.3 s** (range 0.17–0.55 s).

| | 60,000 documents | 500,000 documents |
|---|---|---|
| Background indexing time | **≈ 5 h** (3–9 h) | **≈ 40 h** (24–75 h) |
| Bytes read once (whole files) | ≈ 18 GB | ≈ 150 GB |
| Re-run with nothing changed | 0 bytes read; one pass over the name index (seconds) | same |
| Content store on the system drive | **≈ 0.8–0.95 GB** | **≈ 6.5–7.8 GB** |
| … of which compressed text for snippets | ≈ 0.4–0.55 GB (real prose compresses better than our word salad: 35–45 %) | ≈ 3.5–4.5 GB |
| Worker memory | 50–150 MB, capped at 512 MB (depends on the largest file, not the count) | same |
| Indexer memory | ≈ 20 MB | ≈ 20 MB |
| Query, word in 10 % of documents | ≈ 15–50 ms | ≈ 120–400 ms |
| Query, word in half of the documents (worst case) | ≈ 100–250 ms | ≈ 0.8–2 s |

The design doc's earlier estimate for 60,000 documents (1–2 h) assumed faster extraction and
no antivirus cost; this one is higher because it adds Defender and scales the measured CPU.
The app only indexes while its window is open, so 5 h or 40 h is spread over days of use;
search by name is never affected.

**Main risks from these figures.**

1. **Query latency at 500,000 documents.** FTS5 scores every match, so a common word over a
   large archive misses the 150 ms budget. Tantivy (block-max WAND, measured p95 3 ms at
   20,000 documents) avoids that. Recommendation: keep FTS5 while the archive is under about
   **100,000 documents**; above that, move the full-text rows to Tantivy (or add a two-step
   ranking) before shipping. The Fase 2 document count decides; the store layout (text and
   chunks in SQLite) stays the same either way.
2. **Defender** is the largest unknown per file; measure it on the PC (time to open and read
   1,000 documents with and without the folder excluded).
3. **Disk on the system drive**: 1 GB at 60,000 documents is fine; 7–8 GB at 500,000 may not
   be. Most of it is the text kept for snippets (open question Q3).
